# SBR / RBS implementation and rollout

SBR is SELL after a completed support break and confirmed M5 retest as resistance. RBS mirrors this as BUY. Detection uses the existing `detectStructure` confirmed two-sided pivots, first close crossing, six setup frames (M15/M30/H1/H4/W1/MN1), last-12-bar search and strictly higher directional context. Pivots are confirmed before the breakout; a later bar cannot retroactively qualify a pivot.

Entry uses the existing level-pattern convention: the full completed M5 rejection candle, current ask for BUY / bid for SELL within that zone, maximum width 80 pips (8.00 price). The shared HNS rejection function retains its 25% directional body, 65% close location, two-point level clearance, prior M5 high/low break, contiguous previous M5, freshness and reclaim checks. HNS behaviour and all existing strategy stop calculations remain unchanged.

The SBR/RBS stop is independent of entry-zone width: scan backwards from the candle immediately before breakout to the original confirmed level anchor, choosing the **last candle whose low–high contains that exact level**. Use only that candle's upper wick for SELL or lower wick for BUY. Place the stop at the next broker point strictly outside that wick. There is no 30-pip buffer or 30/50/80-pip risk cap. If the stop is not beyond the entire entry zone, withhold the signal. Breakout/retest candles never become the reference.

Plans include `roleReversal` (`sbr-rbs-v1`): original level and pivot anchor, reference candle timestamp/OHLC, breakout and retest times. SQL recomputes these from the snapshot, checks broker precision and the stable source ID, then applies existing independent three-nearest-intact M30/H1/H4 target checks, freshness, bid/ask and transactional publication. Audit records preserve the proof and all three TP explanations. Rejected candidates record bounded market-only reasons under `engine.sbr_rbs_rejected` in worker logs; no account data or complete snapshots are logged.

The live adapter retains HNS/CH priority, then specific SBR/RBS before overlapping BOS/CHOCH, and its existing one-per-frame/direction/confirmation selection. Stable IDs omit the retest timestamp. SQL also suppresses cross-strategy duplicates sharing a breakout or confirmation with an existing SBR/RBS/BOS/CHOCH publication, including closed signals, inside the existing advisory lock. Existing retired source IDs continue preventing exact replay after retention.

## Rollout order

1. Run the complete migration chain in staging and the engine/SQL tests. Apply `20261113110452_sbr_rbs_last_touch_stops.sql` to the target database **before** deploying the new web/worker commit. It adds strategy constraints, a private invoker validator and a schema capability marker, and patches the existing publication RPC with checked prerequisites. It neither enables publication nor changes historical signals or the owner's policy approval.
2. Verify `automatic_engine_policy.version` remains `vestrado-structure-v1` and `role_reversal_schema_version` is `sbr-rbs-v1`. Confirm the validator is not executable by anon/authenticated/service_role directly; the service-only existing publication RPC invokes it internally. Validate a synthetic/replayed snapshot in staging, including rejection cases and push-outbox dedup; do not send historical production pushes.
3. Deploy the same tested commit to the web service and push/engine worker. New code withholds SBR/RBS when the capability marker is absent, while existing strategy scans/monitoring continue. An older worker remains compatible with the additive database migration. The existing enabled/approved engine policy still governs all publication; **no new engine-policy activation is required**.
4. Check actual worker decisions, audit evidence, notification outbox and tracking on fresh eligible data. Deployment health is not proof that an SBR/RBS signal has been published or that it is profitable.

Rollback the application commit if necessary; retain the additive migration so already-published SBR/RBS records and monitoring remain readable. Do not remove strategy constraints or rewrite existing signals. This implementation/commit does not itself deploy or activate production changes.
